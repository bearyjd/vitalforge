## Carried forward — new since 2026-09-12

### Adoption is once-only, by marker, and moves the file

`bootstrap_legacy_token_store()` runs in both lifespans. Under `legacy_store_flock` →
`person_flock(primary)` it verifies the flat `.garth/garmin_tokens.json` resumes, moves it to
`person-<id>/generation-1/`, publishes an ordinary `linked` row, and writes the
`legacy-garth-store-adopted` marker to `auth_migrations` in the same transaction. The marker,
not the file and not a link row, is what makes it one-time: unlink, relink, archive, promotion,
or a restored `.garth` backup never re-adopts. A crash between the move and the commit is
completed on the next boot without moving again. `legacy_bound`/`legacy_disabled` are retired
in code but stay in the `garmin_links` CHECK — SQLite cannot alter a CHECK on databases that
already created the table, and dev databases did.

### Generations are reserved before the login

`link()` upserts `garmin_link_generations` to its new number **before** the credential login
runs, so a cancelled or failed attempt burns a number and a stale login thread can never write
its client or tokens under a generation a later link publishes. `_publish_link` checks the
ledger still equals the reserved number and the link row is older. Do not "simplify" this
back to computing the generation at publish time.

### The error vocabulary has one home

`shared/garmin_registry_errors.py`: `REGISTRY_ERROR_CODES` (four codes, also the
`garmin_links.last_auth_error` CHECK — bound by a test), `STRENGTH_GARMIN_ERROR_CODES` (13
codes, **append-only**: migration 004 rewrites anything outside it to `unknown` on databases
that have not run it yet), `LEGACY_GARMIN_TARGET_RETIRED_ERROR`. `shared/migrations.py`
imports them under the old local names so the immutable migration bodies are byte-identical.

### `_error_code` classifies by type, then by cause, then by message

`GarminConnectTooManyRequestsError` → `rate_limited`; `GarminConnectAuthenticationError` →
`auth_failed` **unless** its `__cause__` chain carries its own verdict (a 403/5xx
`GarminConnectConnectionError`, a transport error) — garminconnect wraps *any*
profile-fetch failure in that type; 401 → `auth_failed`, 403 → `network` (Cloudflare
challenge), else `network`. Write-path statuses (`Client.post` is undecorated, no `.response`)
come only from the `"API Error NNN"` message text — that dependency is #65.

### Garmin operations run in a worker thread

`_run_operation` does `await asyncio.to_thread(op, client)`. Ops set/reset the
`_operation_client` ContextVar inside their own body, so the seam survives the thread hop.
Consequence documented in `vitalforge_weight/garmin_claim.py`: the SDK's own per-request
timeouts (~60 s warm, ~185 s cold worst case) bound a push well inside the 600 s claim; **do not**
wrap the op in `asyncio.wait_for` — it cannot stop the thread and would clear the claim while
the push may still land.

  (a Proxmox VM, tailnet name `proxy`, no SSH key for us). `192.168.1.11` is a monitor polling
  `/` on both services — never trust it as a proxy.
- Stop both services before pulling: after 003 the old weight image 500s on every activity
  route. Rollback after 003 = restore a snapshot, not an older image (the markers boot-loop).
- Verify a deploy by the image label (`org.opencontainers.image.revision`), by
  `docker compose logs | grep -E "Applied schema migration|Adopted the legacy"` (exactly one
  `Adopted` line across both services; the other logs `skipped: marker already recorded`), and
  by listing `/app/data/.garth/person-1/generation-1/` **by name only**.
- `sync_status.last_sync_time` is the sync's **start** time. A watcher that waits for a
  timestamp after the start will never fire.
- The unauthenticated "is the proxy trusted?" probe (`POST …/api/garmin/link {}` expecting
  400 vs 401) is inconclusive: the auth middleware answers 401 before route dependencies run.
  Check the source IP the app logged for the proxied request instead.

## Things I got wrong, recorded so they are not re-derived

1. **My first fix design had a hole that only the independent re-review found.** Adoption
   moved the flat store under `legacy_store_flock` alone; a concurrent route `link()` for the
   primary could have its freshly published token file overwritten by the legacy account's
   tokens. Two fresh reviewers reproduced it independently. The `independent-review-before-
   merge` rule exists for exactly this: the fix commit is unreviewed by construction.
2. **My marker test was vacuous** — the ledger row for the same person masked the marker, so
   deleting both marker checks left the test green. Fixed by testing the promote-then-archive
   scenario (a different person) and proving it by mutation. A test that passes with the
   guard removed is not a test of the guard.
3. **I planned to narrow the `garmin_links` CHECK** to the single live state. SQLite cannot
   alter a CHECK; dev databases already had the three-state table; the "fix" would have been an
   invisible fresh-vs-existing drift. Caught before any edit.
4. **My plan's `_ensure_token_dir` snippet was wrong**: `Path.mkdir(parents=True, mode=0o700)`
   applies the mode to the leaf only. The implementer kept the test and walked the ancestors.
5. **My plan's RED test for the worker-thread change could not fail** — it released the
   blocked op from the frozen loop, so the release only fired after the op's own timeout and
   the test passed on unpatched code. The implementer rewrote it to release from an OS thread.
6. **I dispatched seven specialists without telling them to write findings to a file.** Five
   results truncated at 16 KB; two re-ask turns died on `ECONNRESET`. The files were the only
   reason nothing was lost. Now in memory as a standing rule.
7. **My deploy watcher matched on the wrong timestamp** (see Deploying).
8. **I nearly deleted the SDD workspace on merge**, which would have taken the twelve rulings
   and the final review with it. Archived to the session scratchpad first; the rulings are in
   the session's closing message and, where they matter, in the commit messages.
