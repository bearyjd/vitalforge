## What landed

### #72 — the registry split (closes #64)

`shared/garmin_registry.py` was 786 of the 800-line ceiling and reached back into itself through two
`_registry()` function-local import shims. Now a one-way DAG, every import at module top:

```
errors / locks / common (leaves)
  -> garmin_registry_runtime    permits, link-attempt quota, auth stamps, _error_code,
                                _validate_link_target, _publish_link
  -> garmin_registry            facade: GARTH_TOKEN_DIR + token-path helpers, lock paths +
                                person_flock / legacy_store_flock, link/relink/unlink, call,
                                call_paced, resolve_token_dir
  -> garmin_registry_legacy     the one-time .garth adoption; imports the facade, never the reverse
  -> both app.py lifespans
```

New: `garmin_registry_common.py` (55) and `garmin_registry_legacy.py` (333). `garmin_registry_locks.py`
became a root-agnostic leaf (123) with one `flock_scope(local_key, lock_path)` primitive replacing two
copies of the acquire/shield/close body.

**The one behaviour change in it, and why:** process-local lock keys are structural tuples
(`("legacy-store",)` / `("person", id)`), and `person_flock` refuses a non-positive id *before* taking
any lock. With the old int namespace and the check inside `lock_path()`, `person_flock(0)` entered
inside `legacy_store_flock` awaited the non-reentrant lock it already held — both lifespans hanging at
boot, no log line, if a primary ever had id 0. Reachable only via a hand-edited database, but the
shape was real; `tests/test_garmin_registry_locks.py` pins it and the pre-hardening form fails 4 of 5.

### #75 — the weight trend chart grew the page forever

Reported live on `weight.grepon.cc/p/<slug>/`. The canvas sat inside `.trend-section` beside the
section title with no height and no positioning, while the chart uses `responsive: true,
maintainAspectRatio: false` — in that mode Chart.js sizes the canvas to its **parent's content
height**, and that parent's height was title + canvas. Each resize grew the section, the
ResizeObserver refired: 1038px at +0.5s, 4332px at +2.5s. Fixed with a dedicated
`.trend-chart-wrap { position: relative; width: 100%; height: 140px }`.

The dashboard's `.chart-wrap` has **no** height and is immune for a different reason
(`maintainAspectRatio: true`). Do not converge the two rules — the CSS comment says so.

### #77 — bounded permit waits (closes #74)

Both pre-existing, both found by #72's adversarial review pass.

- A cold `call()` takes two permits: one before the credential login, one for the operation. The
  second wait runs **inside `person_flock`** and was unbounded for every `max_wait_seconds == 0`
  caller (the scheduled sync via `call_paced`, the activity push). Under permit starvation by the
  other service a cold sync pinned that person's flock indefinitely, with a weigh-in for the same
  person queued behind it. `_post_login_deadline` now returns a finite deadline on both arms.
- The clock-regression guard compared a stored slot against *this process's* interval, so a service
  with a shorter `GARMIN_MIN_CALL_INTERVAL_SECONDS` classified every slot its peer wrote as skew and
  granted itself a permit immediately — the deployment-wide budget silently became per-service, with
  no log and no error. It now compares against the clamp maximum.

## Carried forward — new since 2026-09-19

### The layering guard is the thing that keeps the split a split

`tests/test_registry_layering.py` (31 cases, parametrized). Read it before touching any `shared/garmin_registry*.py`:

- `FORBIDDEN_EDGES` is **derived** from `ORDER = (ERRORS, LOCKS, COMMON, RUNTIME, FACADE, LEGACY)`,
  not hand-written. It used to be a literal table, and `RUNTIME: ()` passed every test — silently
  un-enforcing the exact edge #64 removed.
- Both walkers (`_upward_import_violations`, `_smuggled_import_violations`) have **positive probes**
  over inline source strings, because a checker that never matches passes its module-level test
  vacuously. Each probe row exists because that spelling once slipped through: bare `import shared`
  and un-aliased `import shared.x` (both bind `shared` for a call-time `shared.garmin_registry.X`),
  `import importlib[.x]`, `from importlib import import_module`, bare-name use of
  `importlib`/`import_module`/`resolve_name`, `ast.Attribute` calls like `builtins.__import__(...)`
  and `pkgutil.resolve_name(...)`, and relative imports.
- Still **not** caught, by its own docstring: an aliased `import_module`, and `sys.modules`.
- Each module must import alone in a fresh interpreter under an allowlisted env, and that test
  asserts nothing was written to `shared/`, the repo root, or its tmp dirs.

### `MAX_CALL_INTERVAL_SECONDS` is load-bearing, not a constant tidy-up

`reserve_call_permit`'s clock guard is only correct while its ceiling equals the clamp in
`call_interval_seconds()`. As two `60.0` literals, raising the clamp to 120 would make the guard
reject legitimate slots with **no test failing**. Both read
`shared.garmin_registry_common.MAX_CALL_INTERVAL_SECONDS`, and a test pins the coupling.

`MAX_INTERACTIVE_WAIT_SECONDS` (30) bounds **any one** permit wait held under a person flock — a cold
call takes two, with an untimed provider login between them, so the composite hold is two of these
plus that login. The grace floor for a completed login is capped by it for that reason.

### Facade seams that tests patch, and two that no longer reach

The suite monkeypatches on `shared.garmin_registry`: `GARTH_TOKEN_DIR`, `time.time` and
`asyncio.sleep` (stdlib module attributes — process-global, which is why runtime binding them
directly still works), `garmin_client`, `call`, `call_paced`, `link`, `unlink`, `_publish_link`,
`_person_lock_path`, `_reserve_generation`, `_remove_token_dir`, `_remove_person_token_root`.
`FACADE_PATCH_POINTS` guards that they exist — it catches a *lost* attribute, not a seam that stopped
being read through the facade.

**Two stopped being read through it in #72**: `reserve_call_permit` and `actor_has_effective_manage`
are now runtime-bound. No test patches either today; one that does must patch
`shared.garmin_registry_runtime`. The guard's comment says so.

### Deploying (delta to the 2026-09-11 / -09-19 sections)

The runbook is unchanged and has now run three times cleanly. Two additions:

- **`sync_status` has no `status` or `error_message` column.** It is `person_id / last_sync_time /

## Things I got wrong, recorded so they are not re-derived

1. **My fix spec for #74 broke the bound it was meant to respect.** I specified the post-login grace
   as `max(remaining, call_interval_seconds())`; with an interval above 30 that holds the person
   flock for 60s, defeating the `MAX_INTERACTIVE_WAIT_SECONDS` clamp whose entire justification is
   flock-holding. The executor caught it and offered the bounded form rather than shipping the brief
   as written. Read a constant's *rationale*, not just its value, before writing a formula past it.
2. **I told the user a further review cycle would clear the ledger warning. It structurally could
   not.** gstack certifies a review CURRENT only for a cycle that ends with zero edits and zero
   deferred findings, within a 3-cycle cap. On a ~1.7k-line diff every cycle produced fresh
   docstring/test-strength nits (25 → 13 → 11 findings, 0 critical/high throughout), so the cap is
   reached with fixes applied and the row stays STALE. Set that expectation at the *first* gate; the
   honest framing is "three cycles found no production defect", not "one more cycle and it'll be
   green".
3. **Three full review cycles on a refactor had sharply diminishing returns.** Cycle 1 found the
   things that mattered (the lock-key hang shape, a guard blind spot). Cycles 2 and 3 found
   docstring wording and test-strength items — genuinely useful for the guard, but the cost was
   hours and a weekly limit. For a pure refactor with a strong guard test, one cycle plus a red-team
   pass is probably the right stopping point.
4. **A mutation probe ran without its backup existing.** The scratchpad dir had been cleaned between
   rounds, the bare `cp` failed, the mutation still applied to a live uncommitted file, and the
   restore `cp` failed too — recovered by hand-reversing the edit and `cmp`-ing against another
   agent's copy. Chain it: `mkdir -p bak && cp f bak/ && <mutate>`, never as separate statements.
   Same family as the `git checkout` trap in the 2026-09-19 handoff.
5. **I declared the round-4 addendum unapplied based on a grep that raced the executor's write.**
   It had been written a minute earlier. Re-check before reporting a subordinate's work as missing.
6. **Codex's structured review never establishes the gate here.** It returns a clean verdict in prose
   ("No actionable regressions were identified"), which gstack's validator fail-closes as missing
   coverage — three times across three cycles. Expect it; read it as a human signal, never record it
   as a pass. Its adversarial mode does tag findings and did complete twice.
