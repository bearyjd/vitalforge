# Health dashboard roadmap — 25 October 2026

This roadmap is approved for staged delivery. The first release implements **Now 1** and **Now 2** below. The second release implements the personal comparisons, historical bands, and readiness/anomaly explanations in **Next 3**. The third release implements **Next 4**: context notes/tags and one saved routine experiment per profile. The fourth release implements **Next 5**: the on-demand weekly review. Goal controls and later phases remain planned. Deployment is a separate release step. The first goal is to make personal data easier to understand and upload to an AI service the user already chooses. VitalForge's useful foundation is self-hosted Garmin history, profile isolation, and portable data.

## Starting point

The repository already provides 16 metric APIs, CSV/JSON export, readiness with a dashboard tile, rules and optional LLM recommendations (including personal baselines and anomaly findings), goals APIs, a correlations heatmap with scatter plots, FIT import, multi-person access, Garmin links, and scheduled sync. These should be extended rather than rebuilt. Goals have no dashboard controls in the inspected templates/static files; adding those is a small usability opportunity once goal behavior is validated for the selected profile.

The first release adds raw and AI-ready JSON download buttons for 7/30/90-day ranges, an export-content preview, and an expandable data-quality table. The enriched package has its own endpoint, preserving the existing export API. Some body-composition metrics have no dedicated dashboard chart, so expose additional charts only where the user actually needs them.

The package and quality report share definitions and a consistent SQLite snapshot. Coverage uses exactly N inclusive calendar dates ending on today's UTC date; source dates keep their unknown timezone. Latest observations and the latest profile-wide sync attempt are reported separately. No schema migration or new external integration is required. Exporting does not contact Garmin or an AI provider.

The second release compares adjacent equal-length 7/30/90-day periods and displays observation counts and descriptive previous-period ranges. Sparse/stale data suppresses change interpretation; snapshot series are labeled separately. Existing readiness and daily anomaly formulas are reused with explicit observation windows and supporting dates. Goal controls are deferred: targets belong to the account and are reused across profiles, while progress is evaluated for the selected profile. Their future UI must make that account-wide behavior clear, including the effect of edits and deletions.

The third release adds editable daily entries, chart annotations, and explicitly opt-in context export. A saved day with no tags is logged; a date with no entry is unknown. The saved experiment compares same-date metric/context pairs on explicitly logged tagged versus explicitly logged untagged days, reports coverage and confounders, and suppresses differences with fewer than three pairs per group. Plans are labels and dates, not confirmed adherence or treatment recommendations. New tables are additive and compatible with the previous image; existing migration markers remain unchanged. The fourth release adds an on-demand, rules-only weekly review (`GET /p/{slug}/api/weekly-review`, generated only when the user clicks): changes between the last two 7-day periods (suppressed when observations are insufficient), existing anomaly and rule findings that each link metric, period and supporting dates, stale/partial coverage and last sync result, the signed-in account's goals, and one fixed-template, non-diagnostic follow-up chosen by priority (stale data, strongest finding, goal furthest behind). It adds no score, LLM prose or notification and never reads context notes or tags. The fifth release delivers **Following 6**, a printable report (`GET /p/{slug}/report?days=7|30|90`, opened from the dashboard's "Printable report" control in a new tab): server-rendered with a print stylesheet for the browser's Print / "Save as PDF" and no JavaScript needed on the page. It shows the generation date, selected and previous periods, UTC window and Garmin date semantics, last sync attempt, and per metric the display unit (kg, hours, % and provider-score labels kept honest), source, observed/missing days and coverage, current versus previous means (a real zero difference is "stable"; insufficient or stale data is not interpreted), a descriptive previous-period range, a server-drawn sparkline with a values table, and the existing rule findings with their evidence dates plus the not-a-diagnosis limitation. The profile name and your notes and tags are excluded unless you tick "Include profile name" or "Include my notes and tags" (both reset on reload). Goals are never included, there is no public share URL, and the page is `no-store, private`. All report data comes from one profile snapshot covering twice the selected period.

## Priorities and delivery gates

S/M/L indicate relative effort, including validation, not calendar commitments. Deliver one useful slice at a time. Every slice must preserve profile authorization and use synthetic fixtures for tests; never include Garmin credentials, token files, or private database contents in development artifacts.

|---|---|---|---|---|
| **Now 1** | **AI-ready export package:** upload understandable history without explaining each column. Provide a versioned JSON package and a short accompanying data dictionary with metric meaning, source, units, selected period, timezone/date semantics, and coverage. | M | Verify the pending download UI and existing export behavior. | A selected profile's 7/30/90-day package includes only the chosen period; grams and percentages are explicit; missing values stay missing; secrets and identifying profile/account metadata are excluded by default. A preview explains what will leave VitalForge. The current JSON/CSV response remains compatible through a separate enriched format or endpoint. |
| **Now 2** | **Per-metric data quality:** understand whether a chart or conclusion has enough recent data. Show latest observation, latest sync attempt/result, observed days, missing days, and coverage for the selected period. | M | Agree expected sampling and date semantics per metric; reuse sync status. | Fresh observation and successful sync are distinct; unavailable, stale, partial, and empty data have clear states; a real zero never means missing. Export carries the same coverage metadata. Checks cover partial Garmin failures and multi-person sync intervals. |
| **Next 3** | **Personal ranges and period comparisons:** see what changed relative to the user's own history. Add baseline bands and current-versus-previous-period differences to useful charts; surface existing baseline/anomaly findings with their evidence. | M | Quality metadata; existing recommendations/baseline engine. | Each comparison names its windows, units, sample counts, and baseline method; insufficient history suppresses interpretation. Reuse the current readiness score and explain its existing components. Add basic goal controls against existing APIs only after confirming account/person ownership semantics. |
| **Next 4** | **Optional context tags and simple experiments:** record illness, travel, alcohol, late meals, or a chosen routine, then explore patterns. | **Next 5** | **Weekly review:** understand the few changes worth attention and choose one practical follow-up. Summarize metric trends, missing data, existing rule findings, and progress toward selected goals. | M | Quality and comparison work; existing rules/optional LLM engine; tags when present. | Every finding links to its metric, period, and supporting observations. Rules-only output remains useful without an API key; optional LLM prose introduces no unsupported numbers or findings. Empty weeks say so. | **Following 6** | **Shareable clinician report:** bring a concise, readable record to an appointment. Start with a print stylesheet/browser “Save as PDF,” selected dates, units, source, trends, and optional user notes. | S–M | Stable export metadata and comparisons; weekly review can supply the narrative. | A user can preview and print a legible report with coverage and generation date. Preserve original source and reference ranges where supplied. Do not silently merge unlike tests or infer diagnoses from isolated results. |

## Why these choices

The following are product references, not evidence that these features improve clinical outcomes:

- Oura's [Trends](https://support.ouraring.com/hc/articles/360055983614-Using-Trends) and [Tags](https://support.ouraring.com/hc/en-us/articles/360038676993-Using-Tags) illustrate longitudinal exploration and recording context. VitalForge already has correlations and baseline logic; the opportunity is understandable presentation and contextual evidence.
- Oura's [export and sharing guidance](https://support.ouraring.com/hc/en-us/articles/360025441594-Export-Share-Your-Oura-Data) and [reports](https://support.ouraring.com/hc/articles/360046061373-Oura-Reports) provide references for portable data and periodic summaries. Apple's [Health source management](https://support.apple.com/en-mt/108779) supports making provenance and source priority visible when adding imports.
- [Claude remote connector guidance](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp) and [ChatGPT developer mode guidance](https://help.openai.com/en/articles/12584461-developer-mode-and-full-mcp-connectors-in-chatgpt) make remote MCP a possible later integration. Availability and authentication requirements must be checked for the intended account at implementation time.

## Deliberate deferrals

Defer a native mobile app, an embedded chatbot, another readiness score, automatic medical alerts, write-capable AI tools, and broad wearable/lab integrations. The PWA, existing engine, and export workflow can answer the immediate need with less maintenance. Revisit notifications after weekly reviews prove useful, and revisit remote MCP only when repeated manual uploads become a clear burden.

Before each implementation slice, confirm scope and review the affected code. Changes in shared auth/database/Garmin modules must be checked against both services; migrations need their own upgrade/concurrency plan. Validate API compatibility, profile isolation, sparse/missing data, and the relevant UI before calling a slice complete.
